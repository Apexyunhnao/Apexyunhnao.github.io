企业内网 RAG 的三个真相：表格解析、权限隔离、审计

2026-10-17 · 实测记录 · 4 份真实港股公告 + Dify 1.17 + 本地 7B 模型

给「数据不能出内网」的场景做 RAG，最大的误区是以为难点在模型。实际跑下来， 三个真正卡人的地方分别是：文档解析、权限隔离、审计设计——而且每一个都有 「看起来解决了、实际没解决」的陷阱。

真相一：港股公告的表格，主流解析库一个都认不出来

从港交所下载 4 份真实公告（收购、持续关连交易、出资协议），用 pdfplumber 跑一遍：

公告页数字符数识别出的表格
七色珠光收购169,1220 个
中铝合资105,1760 个
中海油服框架协议1611,3070 个
立讯持续关连交易169,4960 个

原因很简单：港股公告的表格没有任何框线。我用 pymupdf 数了每页的线条数量，全部是 0。 这些表格靠空白对齐，而 pdfplumber 默认按线条识别，自然一个都认不出来。

换 vertical_strategy="text" 反而更糟——它会过度切分，把正文切成假表格：

表头识别结果：
  ['香', '港交易及結算所有限公司及香港']
  ['', '']
  ['準', '確性或完整性亦不發表任何聲明']

更麻烦的是，即使不识别表格，原始文本流也会把表格彻底打散。同一份公告的表格提取出来是这样：

建議年度上限
673
734
804
363
429
484

模型看到「363」不知道是哪个项目、哪一年。这就是所有 RAG 项目里最典型的一句话：表头和数据行分离。

解法：按坐标重建，再拆成事实句

用 word 的 bbox 按 y 聚行、按 x 对齐表头列，重建出「项目｜列名｜数值」： 

中國海油集團向本集團提供物業服務｜建議年度上限｜截至2026年12月31日止年度｜363
中國海油集團向本集團提供物業服務｜歷史交易金額｜截至2025年6月30日止六個月｜86

同一份公告、同一个 qwen2.5:7b，两种喂法对比：

喂法准确率失败模式
Markdown 表格3/4缺列时模型数错位置（2026 取成 2027 的值）
事实句4/4—
教训：我人工核对 PDF 表格对齐时错了两次——先把 2026 的值当成 2025H1， 又把 363 当成 2025H1，中途还一度以为是模型答错。按坐标实测才发现脚本一直是对的。 这类表格不能靠「人看一眼觉得对」来验收，必须坐标级对齐。

真相二：社区版 Dify 做不了「同一个库里按人隔离」

Dify 的知识库绑定在应用配置里，chat API 不能动态指定知识库，也没有片段级 metadata 过滤。 这意味着「合规部能看内审报告、人事部看不到」这个需求，在社区版上没有直接解法。

可行的落地方式只有一个：一个密级一个知识库 + 一个应用，前面挂权限网关按身份路由。

用户 → 权限网关(:8090) → 查部门 → 选对应应用 → Dify /v1/chat-messages
                       → 审计（谁/何时/走哪个库/是否拦截/耗时）

用户拿不到 app key，也不能直连 Dify。这比「片段级过滤」更硬——越权用户提问时， 检索发生在**他自己的库**里，敏感文档根本不在候选集中：不是查出来再隐藏，而是从来没被检索过。

实测（同一问题「关联交易审批存在什么问题」）：

身份路由回答耗时
合规部合规知识库违反《上市规则》14A.35 条1.4 s
人事部人事知识库未提及0.5 s
访客—HTTP 4030 ms
无效令牌—HTTP 4010 ms

补充一个细节：最初网关直接信任请求体里的 user 字段，等于谁都能冒充。 改成 Bearer 令牌后，身份只从令牌推导，请求体声明与令牌不符直接 403。 这类权限设计必须先假设「请求可以被伪造」。

代价要说清楚：分库方案的库数量随密级增长（部门 × 密级）。 密级超过 5 个时维护成本会爆，那时该考虑企业版或自研检索层，而不是硬扛。

真相三：「审计只存哈希」会被数据库自己的表打穿

网关的审计日志我按「只记行为、不存原文」设计——问题只存 SHA256 前 16 位和长度。 看起来很干净，直到我查了 Dify 自己的表： 

SELECT query, left(answer, 40) FROM messages ORDER BY created_at DESC LIMIT 3;

query  = "陈大文的月薪是多少"
answer = "陈大文的月薪是128,000港元。来源文档：员工花名册（人事部专用）。"

messages 表里存着完整的问答原文。也就是说，「审计不存原文」只是我的网关不存， 系统整体是存的。

处理方式不是删——泄密调查恰恰需要原文。正确的做法是把它写进制度：

  • 留存多久
  • 谁能查
  • 查要谁批准

而对外不能宣称「系统不存原文」。这句话一出，出事时就成了把柄。

一条必须承认的边界

无论审计做得多细，有服务器 root 权限的人都能直接 docker exec 进容器读数据库、 读模型缓存。这不是技术方案能解决的问题，是运维制度和权限分离的问题。

所以给这类项目做方案时，负责任的说法是： 技术保证「数据不出内网 + 越权检索不到 + 行为有记录」， 制度保证「谁能碰服务器 + 留下什么记录」。把这两层混在一起讲，就是过度承诺。

这套东西能做什么、不能做什么

能不能
本地模型直接读敏感原文（能力不打折）防住有 root 权限的人
越权用户在检索层就被挡住字段级权限（只看摘要不看数字）
谁查了什么有记录靠模型能力精确拆解复杂合并单元格表格
断网环境可运行（有自检脚本与网络审计）跨库关联查询（要显式建联合视图库）
